📖 Notes
What is backend architecture?
Backend architecture is the way we organize different responsibilities of an application into separate parts.
Instead of putting everything inside one large file, we separate:
Routes
Controllers
Services
Middleware
Data / Database
This makes the application easier to understand, test, maintain, and scale.

Why should business logic not live entirely inside controllers?
As the application grows, controllers can become very large if they contain:
HTTP handling
validation
business logic
database operations
error handling

This makes the code difficult to maintain.
Instead:
Controller
    ↓
Service
    ↓
Data / Database
The controller handles HTTP-related work while the service handles business logic.

What is a service layer?
A service layer contains the business logic of the application.
For example:
getMissionById(id)
The service can find the mission without knowing anything about:
req
res
res.json()
This makes the business logic reusable.
The same service could later be used by:
HTTP API
Tests
Background jobs
Other application features

Controller vs Service
Controller
The controller handles HTTP.
It works with:
req
res
req.params
req.query
req.body
HTTP status codes
Example:
export function getMissionById(req, res) {
    const id = Number(req.params.id);
    const mission = findMissionById(id);
    if (!mission) {
        return res.status(404).json({
            error: "Mission not found"
        });
    }
    res.json(mission);
}

Service
The service handles business logic.
Example:
export function getMissionById(id) {
    return missions.find(
        mission => mission.id === id
    );
}

The key difference is:
Controller → HTTP logic
Service    → Business logic

What is middleware?
Middleware is a function that runs during the request-response lifecycle.
Example:
app.use((req, res, next) => {
    console.log(req.method, req.url);
    next();
});

Middleware can:
inspect requests
modify requests
validate data
authenticate users
log requests
parse data
handle errors
pass control to another middleware

What is validation middleware?
Validation middleware checks incoming data before the request reaches the controller.
Example:
export function validateMission(req, res, next) {
    const { title, difficulty } = req.body;
    if (!title || !difficulty) {
        return res.status(400).json({
            error: "title and difficulty are required"
        });
    }
    next();
}

The request flow becomes:
Request
   ↓
Validation middleware
   ↓
Controller

If the data is invalid:
Request
   ↓
Validation middleware
   ↓
400 Bad Request
The controller never runs.

Why is frontend validation not enough?
Frontend validation can be bypassed.
A user can directly call the API using:
Postman
curl
another application
custom JavaScript
Therefore validation must also happen on the server. The frontend improves user experience. The backend protects the application.

What is next()?
next() passes control to the next middleware or route handler.
Example:
app.use((req, res, next) => {
    console.log("Request received");
    next();
});
Without next() or a response, the request can become stuck.

Flow:
Middleware
    ↓
next()
    ↓
Next middleware / route

What is next(error)?
next(error) tells Express that an error has occurred.
Example:
app.get("/api/test-error", (req, res, next) => {
    next(new Error("Database connection failed"));
});
This skips the normal middleware flow and sends the error to Express error-handling middleware.

Flow:
Route
   ↓
next(error)
   ↓
Error handler
   ↓
Error response

Difference between next() and next(error)
next()
   ↓
Continue normal execution

next(error)
   ↓
Enter error-handling flow
This distinction is extremely important in Express.

What is centralized error handling?
Instead of writing:
try {
    ...
} catch (error) {
    res.status(500).json(...)
}
inside every controller, we can create one centralized error handler.
Example:
export function errorHandler(err, req, res, next) {
    console.error(err);
    res.status(err.status || 500).json({
        error: err.message || "Internal server error"
    });
}

Now errors can be passed to one place:
next(error);
This avoids duplicated error-handling code.

Why does error middleware have four parameters?
Error-handling middleware has the signature:
(err, req, res, next)
The four parameters are:
err  → the error
req  → request
res  → response
next → next middleware
Example:
function errorHandler(err, req, res, next) {
    console.error(err);
    res.status(500).json({
        error: err.message
    });
}
Express recognizes the four-parameter form as error-handling middleware.

What is a 404 error?
A 404 Not Found means the requested route or resource could not be found.
Example:
{
    "error": "Route not found"
}

Example request:
GET /api/does-not-exist

What is a 500 error?
A 500 Internal Server Error means an unexpected problem occurred on the server.
Example:
{
    "error": "Database connection failed"
}
So: 404 → Route/resource not found
500 → Unexpected server-side failure

Why should 404 middleware come after the routes?
Express processes middleware from top to bottom. If the 404 middleware comes before the routes:
Request
   ↓
404 middleware
   ↓
Route never gets a chance

Correct order:
JSON middleware
      ↓
Logger
      ↓
Routes
      ↓
404 middleware
      ↓
Error middleware

What is a 404 middleware?
Example:
export function notFound(req, res) {
    res.status(404).json({
        error: "Route not found"
    });
}
It runs when no previous route handled the request.
Complete Express request flow For a POST request:
POST /api/missions
        ↓
Express receives request
        ↓
express.json()
        ↓
Validation middleware
        ↓
Route
        ↓
Controller
        ↓
Service
        ↓
Data / Database
        ↓
Service returns result
        ↓
Controller
        ↓
HTTP response
        ↓
Client

If an error occurs:
Controller / Service
        ↓
next(error)
        ↓
Centralized error handler
        ↓
500 response

Consistent API responses
An API should ideally use predictable response structures.
Success example:
{
    "success": true,
    "data": {},
    "message": "Mission created successfully"
}

Error example:
{
    "success": false,
    "error": "Mission not found"
}
Consistent responses make frontend integration easier.

Server-side security principle
Never trust: req.body just because it came from your frontend.
A malicious client can send unexpected data directly to your API.
For example:
{
    "title": 12345,
    "difficulty": {
        "bad": "data"
    }
}
The server must validate the input itself.

What is MongoDB?
MongoDB is a NoSQL document database used to store application data persistently.
Unlike the temporary JavaScript array:
const missions = [];
MongoDB stores data outside the Node.js process. Therefore data can survive server restarts.

MongoDB hierarchy
The structure is:
Database
   ↓
Collection
   ↓
Document
   ↓
Fields

For Developer OS:
developer_os
   ↓
missions
   ↓
{
    title: "Learn Express",
    difficulty: "hard"
}

Database
Container for related collections.
developer_os

Collection
Stores related documents.
missions

Document
Represents one record.
{
    "title": "Learn Express",
    "difficulty": "hard"
}

Field
An individual piece of information.
title
difficulty

What is Mongoose?
Mongoose is an ODM library that provides a structured way for Node.js applications to work with MongoDB.
It provides:
schemas
models
validation
database operations

What is a Mongoose Schema?
A schema describes the structure and rules of a document.
Example:
const missionSchema = new mongoose.Schema({
    title: {
        type: String,
        required: true,
        minlength: 5,
        trim: true
    },
    difficulty: {
        type: String,
        required: true,
        enum: ["easy", "medium", "hard"]
    }
});
This means:
title
→ String
→ required
→ minimum 5 characters
→ whitespace trimmed

difficulty
→ String
→ required
→ only easy/medium/hard

Why use validation at multiple layers?
The application now has:
Client
   ↓
Express validation
   ↓
Service
   ↓
Mongoose validation
   ↓
MongoDB

Express validation rejects bad requests early.
Mongoose validation protects the data model.
This provides an additional layer of protection.

The application depends on the database.
Therefore:

❓ Questions
Q1. Why shouldn't business logic live entirely inside controllers?
Because controllers become difficult to maintain as the application grows. Separating business logic into services keeps the code organized.

Q2. What is the purpose of a service layer?
It separates business logic from HTTP-specific code.

Q3. Why is frontend validation not enough?
Because a user can bypass the frontend and directly send requests to the backend.

Q4. What is validation middleware?
Middleware that checks incoming data before allowing the request to reach the controller.

Q5. What is the difference between next() and next(error)?
next() continues normal middleware execution, while next(error) passes an error into Express's error-handling flow.

Q6. Why does error middleware have four parameters?
Because Express recognizes:
(err, req, res, next)
as error-handling middleware.

Q7. What is the difference between 404 and 500?
404 means the requested route or resource was not found. 500 means an unexpected server-side error occurred.

Q8. Why should the 404 middleware come after the routes?
Because Express executes middleware in order. The routes need a chance to handle the request before the application declares it missing.

Q9. What is the difference between a controller and a service?
A controller handles HTTP requests and responses, while a service handles business logic.

Q10. Explain the complete POST flow.
A POST request reaches Express, express.json() parses the JSON body, validation middleware checks the data, the router selects the controller, the controller calls the service, the service performs the business logic, and the controller sends the HTTP response back to the client.

📖 Notes
What is a Role?
A role represents a category of permissions assigned to a user.
For example:
user
admin
A normal user might manage their own missions.
An administrator might manage missions belonging to every user.

What is RBAC?
RBAC means:
Role-Based Access Control
The application determines permissions based on the user's role.
The concept is:
User
 ↓
Role
 ↓
Permissions

For example:
User
 ↓
user
 ↓
manage own missions
and:
User
 ↓
admin
 ↓
manage all missions

Authentication vs Authorization vs Ownership
These are three different concepts.
Authentication
Answers:
Who are you?
Example:
JWT
 ↓
verify
 ↓
req.user

Ownership
Answers:
Do you own this particular resource?
For a mission:
mission.createdBy
        ↓
req.user._id
If they match, the user owns the mission.

Role Authorization
Answers:
Does your role give you permission to perform this operation?
Example:
req.user.role
      ↓
   admin?
So:
Authentication → identity
Ownership → resource relationship
Authorization → permission

Why Should the Client Not Choose the Role?
Suppose the registration request contains:
role = admin
If the server blindly trusts that value, anyone could create an administrator account.
That would be a serious security problem.
Therefore:
Client
 ↓
name
email
password
The server decides:
role = user
The client does not decide its privilege level.

Safe Registration Principle
Avoid creating a User directly from the entire request body.
Conceptually:
Bad:
req.body
 ↓
User.create()
because the body may contain fields the client should not control.
Instead, explicitly select the fields that the client is allowed to provide:
name
email
password
Then create the User.
The schema supplies the default:
role = user

What Happens When a Client Sends role: admin?
Suppose Postman sends:
name
email
password
role = admin
The server should ignore the role during normal registration.
The resulting user should still have:
role = user.
The security flow is:
Client sends admin
       ↓
Server ignores client-controlled role
       ↓
User model default
       ↓
role = user

How Does Someone Become an Admin?
Normal registration should never create an admin.
Instead, an authorized administrative operation can change the role later.
Conceptually:
Admin
 ↓
admin-only endpoint
 ↓
change user role
 ↓
user becomes admin
The operation itself must be protected.
Otherwise a normal user could simply call it and promote themselves.

Admin Middleware
an admin middleware can perform another check:
req.user.role
 ↓
admin?
If the role is admin:
next()
Otherwise:
403 Forbidden

Middleware Chaining
Express allows multiple middleware functions to execute in sequence.
For an admin-only route:
Request
 ↓
validateUser
 ↓
requireAdmin
 ↓
Controller
First:
validateUser
answers:
Is this user authenticated?
Then:
requireAdmin
answers:
Is this authenticated user an administrator?

Why 403 for a Non-Admin?
A normal user may already be authenticated.
For example:
JWT valid ✅
User exists ✅
role = user
But they are not allowed to access an admin operation.
Therefore:
403 Forbidden

401 vs 403
401 Unauthorized
Authentication failed or is missing.
Examples:
No token
Invalid token
Expired token
User no longer exists
Meaning:
The server cannot authenticate the request.

403 Forbidden
Authentication succeeded, but the user doesn't have permission.
Examples:
Normal user accessing admin route
Authenticated non-owner modifying another user's mission
Meaning:
The server knows who you are, but you aren't allowed to perform the operation.

Authorization Should Use Server-Side Identity
Do not authorize using:
req.body.role
because the client controls the request body.
Use:
req.user.role
because req.user comes from the verified authentication process.
The flow is:
JWT
 ↓
jwt.verify()
 ↓
User lookup
 ↓
req.user
 ↓
req.user.role

Why Role Changes Are Sensitive
Changing:
user → admin
increases the user's privileges.
Therefore role changes should be treated as security-sensitive operations.
A normal user should not be able to modify their own role through an ordinary profile update.

📖 Notes
1. What is an Index?
An index is a data structure that MongoDB uses to find documents more efficiently.
Without an appropriate index, MongoDB may have to examine many or all documents in a collection to find the required documents.
An index works similarly to the index of a book.
Instead of reading every page to find a topic, the book index tells us where the topic is located.
The same general idea applies to MongoDB.

2. Why do we need indexes?
Indexes become important when a collection becomes large.
For a small collection containing only a few documents, a collection scan might still be extremely fast.
But as the number of documents grows, repeatedly examining every document becomes increasingly expensive.
Indexes can reduce the amount of unnecessary work MongoDB performs for supported queries.

3. What happens without an index?
MongoDB may perform a collection scan.
A collection scan means MongoDB checks documents in the collection to determine which ones match the query.
For example, if a collection has many documents and we search for missions with a particular difficulty, MongoDB may need to examine a large portion of the collection.
This is represented in query execution as:
COLLSCAN

4. What is COLLSCAN?
COLLSCAN means Collection Scan.
It means MongoDB is scanning the collection rather than using an index to locate the matching documents.
A collection scan can be acceptable for small collections, but it may become expensive as the amount of data increases.

5. What is IXSCAN?
IXSCAN means Index Scan.
It means MongoDB is using an index to locate matching records.
Instead of examining the collection directly, MongoDB can use the index to find the relevant entries.
This can greatly improve performance for suitable queries on larger datasets.

6. COLLSCAN vs IXSCAN
COLLSCAN
MongoDB examines documents in the collection.
Collection → examine documents → find matches

IXSCAN
MongoDB examines the appropriate index.
Index → find relevant entries → retrieve documents
Therefore:
COLLSCAN = collection scan
IXSCAN = index scan

7. What is a single-field index?
A single-field index is an index created on one field.
For example, your Mission API frequently filters missions by difficulty.
Therefore, difficulty is a possible candidate for an index.
The purpose is to make frequently used filtering operations more efficient.

8. Why was difficulty a good index candidate?
Your API frequently supports queries based on mission difficulty.
For example:
GET /api/missions?difficulty=hard
Because this field is actively used for filtering, it is a good candidate to investigate for indexing.
Your MongoDB Compass test demonstrated the difference.
Before indexing:
COLLSCAN
After indexing:
IXSCAN
The query was then able to use the difficulty index.

9. Why shouldn't we index every field?
Indexes are not free.
Each index consumes resources such as:
storage
memory/cache
database maintenance work
When documents are inserted, updated, or deleted, relevant indexes also have to be maintained.
Therefore:
More indexes do not automatically mean better performance.
Indexes should be created based on actual query patterns and performance requirements.

10. What is explain()?
explain() allows us to inspect how MongoDB executes a query.
It helps us understand the query's execution plan.
It can tell us things such as:
whether MongoDB used an index
whether it performed a collection scan
how many documents were examined
how many index keys were examined
how many documents were returned
execution time
execution stages
This allows us to measure database performance instead of guessing.

11. Why is explain() important?
Suppose a query feels slow.
We should not immediately create an index.
Instead:
Run the query → inspect the execution plan → identify the problem → optimize → measure again
This makes database optimization evidence-based.

12. What does documents examined mean?
It tells us approximately how many documents MongoDB had to inspect while executing the query.
For example:
Documents examined: 4
means MongoDB examined four documents.
A useful goal is often to reduce unnecessary document examination for frequently used queries.

13. What does index keys examined mean?
When MongoDB uses an index, it examines index entries to find matching documents.
The execution statistics can tell us how many index keys were examined.
This helps us understand how efficiently the index is being used.

14. What is a compound index?
A compound index is an index that contains multiple fields.
For example, an application might frequently:
filter by difficulty
sort by creation date
A compound index can be designed around that query pattern.
Therefore:
Single-field index → one field
Compound index → multiple fields

15. Why does field order matter in a compound index?
The order of fields in a compound index affects how MongoDB can use that index.
For example:
difficulty + createdAt is not equivalent to: createdAt + difficulty
The order affects the index's ability to efficiently support different filtering and sorting patterns.
Therefore, compound indexes should be designed based on the actual queries the application runs.

16. What is schema design?
Schema design means deciding how application data should be structured in MongoDB.
It includes decisions such as:
which fields belong in a document
which data should be embedded
which data should be referenced
which fields should be indexed
how entities should relate to one another
Good schema design depends heavily on how the application reads and writes the data.

17. What is embedding?
Embedding means storing related data directly inside another document.
For example, a User document might contain its address as a nested object.
Conceptually:
User → profile information → address
The address exists directly inside the User document.

18. When should we use embedding?
Embedding is useful when:
the nested data strongly belongs to the parent
the nested data is usually accessed together with the parent
the nested data is not independently shared
the nested data is relatively small
For example, an address can often be naturally embedded inside a User document.

19. What is referencing?
Referencing means storing a reference to another MongoDB document instead of duplicating the entire related document.
For example:
Mission → createdBy → User ID
The mission stores the User's _id.
It does not need to store the entire User object inside every mission.

20. Why are references useful?
Suppose one User creates 1,000 missions.
Without references, we could end up duplicating the user's information inside every mission.
With a reference:
User → one user document
and:
Mission 1 → User ID
Mission 2 → User ID
Mission 3 → User ID
and so on.
This reduces duplication.

21. Referencing and SQL foreign keys
A MongoDB reference is conceptually similar to a foreign key in a relational database because one document stores the identifier of another entity. However, MongoDB references are not exactly the same as SQL foreign keys.
MongoDB does not provide the same relational database behavior automatically.
The important idea is simply:
One document stores the ID of another document.

22. Embedding vs Referencing
Embedding
The related data is stored inside the parent document.
Parent → nested child data

Referencing
The parent stores the ID of the related document.
Parent → related document's ID
The choice depends on how the application uses the data.

23. When should we use referencing?
References are useful when the related entity:
exists independently
is shared by many documents
changes independently
is relatively large
would otherwise be duplicated many times
Your User → Mission relationship is a good example.
One User can create many Missions.

24. When should we use embedding?
Embedding is useful when the related data:
belongs strongly to the parent
is small
is usually read with the parent
doesn't need to exist independently
isn't shared across many documents
The decision should be based on application access patterns rather than simply saying one method is always better.

25. What is ref in Mongoose?
ref tells Mongoose which model a referenced ObjectId belongs to.
For example: Mission.createdBy → User
The ref tells Mongoose that the ObjectId stored in createdBy belongs to the User model.
So conceptually: createdBy → ObjectId → User
This allows Mongoose to understand the relationship.

26. What is populate()?
populate() tells Mongoose to follow a reference and retrieve the related document.
Without population, the Mission might contain only:
createdBy: User ID
With population, Mongoose can retrieve the User document associated with that ID.
The result can then contain:
User ID
User name
User email
other selected User fields
Therefore:
Reference → stores the relationship
Populate → retrieves the related document

27. Reference vs Populate
This is one of the most important concepts from today.
Reference
The Mission stores:
createdBy → User _id
Populate
Mongoose follows that ID:
Mission.createdBy → User document
So the easiest way to remember it is:
ref = relationship information
populate = follow the relationship

28. Why don't we store the whole User inside every Mission?
Suppose Jayaprakash creates 1,000 missions.
If each mission stores:
name
email
country
other profile information
then the same User information is duplicated 1,000 times.
This causes:
larger storage usage
repeated data
more updates
higher risk of inconsistent information
With a reference, the User information is stored once.

29. What problems can data duplication create?
Suppose the user's email changes.
If the email is duplicated across many mission documents, every duplicated copy would need to be updated.
If one copy is missed, the database could contain inconsistent information.
This is one of the major reasons references are useful for independently managed entities.

30. What is a relationship?
A relationship describes how two entities are connected.
In Developer OS:
User → Mission
A User can create multiple Missions.
Therefore, we have a: One-to-Many relationship
One User: → many Missions
Each Mission: → one creator

31. Developer OS relationship
Your current architecture can conceptually be represented as:
Users collection
User ID
name
email

Missions collection
Mission ID
title
difficulty
createdBy
createdAt
updatedAt
The connection is: Mission.createdBy → User._id

32. Why should the server validate references?
A client might send an invalid User ID.
For example, the client may provide an ID that does not correspond to an existing User.
The backend should eventually verify that the referenced User exists.
This prevents invalid relationships from being stored.

33. Indexing and schema design are connected
Indexing isn't separate from schema design.
You should think about:
How will my application query this data?
Then design:
schema
references
indexes
around those access patterns.
For example, if your API frequently filters by difficulty and sorts by creation time, you can investigate whether an appropriate index supports that query efficiently.

34. Query optimization process
A good optimization process is:
1. Identify an important query
↓
2. Measure it
↓
3. Run explain()
↓
4. Inspect the execution plan
↓
5. Identify unnecessary work
↓
6. Create an appropriate index if needed
↓
7. Run explain() again
↓
8. Compare the results
This is much better than creating indexes blindly.

📖 Notes
What is a Protected Route?
A protected route is an API route that requires authentication before the request can reach the controller.
For example:
POST /api/missions
should require a valid JWT.
The flow is:
Request
   ↓
Authentication middleware
   ↓
JWT verification
   ↓
req.user
   ↓
Controller
Without a valid token, the request is rejected.

Why should createdBy not come from the client?
Previously, a client could send:
createdBy along with the mission.
This is insecure because the client could send another user's ID and pretend that they created the mission.
For example:
User A
   ↓
sends createdBy = User B
The server should never trust this.
Instead:
JWT
 ↓
validateUser
 ↓
req.user
 ↓
req.user._id
 ↓
createdBy
The server determines the owner.

User-Owned Resources
A mission now belongs to a specific user.
The relationship is:
Mission.createdBy
       ↓
User._id
For example:
User A
 ├── Mission 1
 ├── Mission 2
 └── Mission 3

User B
 ├── Mission 4
 └── Mission 5
The application can now determine which missions belong to which user.

Why should "My Missions" be filtered on the backend?
Suppose the database contains missions belonging to multiple users.
An insecure approach would be:
Database
   ↓
All missions
   ↓
Frontend
   ↓
Hide missions belonging to other users
This is not security.

The correct approach is:
Authenticated user
   ↓
Backend
   ↓
filter by user ID
   ↓
return only allowed missions
The frontend should never receive data that the user isn't supposed to access.

What is an Ownership Check?
An ownership check verifies whether the currently authenticated user owns the resource they are trying to modify or delete.
For a mission:
mission.createdBy
        ↓
compare with
        ↓
req.user._id
If they match:
authorized ✅

If they don't:
forbidden ❌

Why is Ownership Business Logic?
The rule: Only the user who owns a mission can modify or delete it. is an application/business rule.
Therefore it belongs in the business-logic/service layer rather than being mixed into basic HTTP handling.
The architecture becomes:
Controller
   ↓
Service
   ↓
ownership check
   ↓
database operation

HTTP 401 vs 403
This distinction is very important.
401 Unauthorized
The request is not successfully authenticated.
Examples:
No JWT
Invalid JWT
Expired JWT
User associated with token no longer exists
Meaning:
"I don't know who you are."

403 Forbidden
The user is authenticated but does not have permission to perform the action.
Example:
User B
   ↓
authenticated ✅
   ↓
tries to update User A's mission
   ↓
403 Forbidden
Meaning:
"I know who you are, but you aren't allowed to do this."

Mission Creation After Authentication
Previously:
Client
   ↓
title
difficulty
createdBy

Now:
Client
   ↓
title
difficulty
   ↓
JWT
   ↓
req.user
   ↓
createdBy = req.user._id
This is much safer.
The client only supplies mission information.
The server determines ownership.

        ↓

        ↓

        ↓

validateMission
        ↓
mission controller

Getting the User's Missions
A protected endpoint can return missions belonging only to the authenticated user.
For example:
GET /api/missions/my
The backend uses the authenticated user's ID to query the Mission collection.
Conceptually:
req.user._id
      ↓
Mission collection
      ↓
createdBy = req.user._id
      ↓
user's missions
This means each user gets only their own missions.

Why distinguish 404 and 403?
A mission can fail the request for two completely different reasons.
Mission doesn't exist
Mission ID
   ↓
No matching document
   ↓
404 Not Found
Meaning:
There is no such resource.

Mission exists but belongs to another user
Mission exists
   ↓
Owner ≠ current user
   ↓
403 Forbidden
Meaning:
The resource exists, but you aren't allowed to modify it.

Update Mission Authorization
The service should:
Find the mission.
Check whether it exists.
Check whether the current user owns it.
Update only if authorized.
This gives a clean decision tree:
Find mission
    ↓
Not found?
    ↓
404


Found
    ↓
Owner?
 ├── No → 403
 └── Yes → update

Delete Mission Authorization
The same ownership logic applies when deleting.
The service should:
Find the mission.
Return notFound if it doesn't exist.
Check ownership.
Return forbidden if another user owns it.
Delete the mission if authorized.
This prevents a logged-in user from deleting somebody else's mission.

PUT Validation
For your current implementation, PUT requires the fields needed to update the mission.
The validation checks things such as:
title exists
title is a string
title has minimum length
difficulty exists
difficulty is valid
So the request is validated before ownership/business logic is executed.

populate() with Missions
Your Mission stores:
createdBy → User._id
If you retrieve a mission normally, you can get only the ObjectId.
If you use populate("createdBy"), Mongoose can retrieve the associated User document.
Without population:
createdBy:
User ObjectId
With population:
createdBy:
{
    name,
    email
}

Why shouldn't every query use populate()?
Population requires retrieving related information.
If the frontend only needs:
title
difficulty
then retrieving the whole User document is unnecessary.
Populate only when the related information is actually needed.

Important Security Principle
Never rely on the frontend to enforce authorization.
The frontend can:
hide buttons
disable controls
display only some data
But none of that provides actual security.
A malicious client can directly call your API.
Therefore the backend must always enforce:
authentication
ownership
authorization
validation

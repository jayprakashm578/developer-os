📖 Notes
What is Authentication?
Authentication answers:
Who are you?
It verifies the identity of a user.
Examples include:
email and password
JWT
sessions
OAuth
The basic login process is:
Credentials
↓
Verification
↓
User identified

What is Authorization?
Authorization answers:
What are you allowed to do?
For example:
User
→ create missions
Admin
→ create missions
→ delete missions
→ manage users
Therefore:
Authentication → identity
Authorization → permissions

Why do we need authentication?
Without authentication, a client could send:
POST /api/missions
and claim to be another user by sending an arbitrary createdBy value.
This is unsafe because the server cannot trust information supplied by an unauthenticated client.
Authentication allows the server to determine the identity of the actual logged-in user.

Why should passwords never be stored directly?
Passwords should never be stored in plain text.
For example, the database should not contain:
password: 123456
If the database were compromised, the original passwords would immediately be exposed.
Instead, passwords should be stored as secure hashes.

What is Hashing?
Hashing converts input into a one-way representation.
Conceptually:
Password
↓
Hashing algorithm
↓
Password hash
The goal is that the original password cannot simply be recovered from the hash.

Hashing vs Encryption
Hashing
Hashing is intended to be one-way.
Password
↓
Hash
The original password is not normally recovered from the hash.

Encryption
Encryption is reversible when the correct key is available.
Data
↓
Encryption
↓
Encrypted data
↓
Decryption
↓
Original data
Passwords generally require hashing rather than reversible encryption.

What is bcrypt?
bcrypt is a password-hashing algorithm/library commonly used for securely hashing passwords.
It can:
hash passwords
compare a plain password with a stored hash
use a salt
apply a configurable work factor

What is a Salt?
A salt is random data used during password hashing.
Conceptually:
Password

- Random salt
  ↓
  Hash
  This means two users who choose the same password can still have different stored hashes.

Why are password hashes different for the same password?
Suppose two users both choose:
password123
Because bcrypt uses a salt, their hashes can still be different.
This makes it harder for attackers to identify users who share the same password.

What is a Cost Factor?
bcrypt has a work factor that determines how much computation is required to generate a password hash.
A higher work factor generally means:
more computation
↓
slower hashing
↓
more difficult password guessing attacks
It is a balance between security and server performance.
User Registration
Registration creates a new user account.
The flow is:
POST /register
↓
Validate input
↓
Check duplicate email
↓
Hash password
↓
Create User
↓
MongoDB
↓
Return safe user data
The password should not be returned to the client.

Why check for an existing email?
If email is being used as the user's login identity, duplicate accounts using the same email should normally not be allowed.
The server should:
Find user by email
↓
Exists?
├── Yes → reject
└── No → create user
User Login
Login verifies an existing user.
The process is:
POST /login
↓
Find user by email
↓
Get stored password hash
↓
Compare password
↓
Correct?
├── No → 401
└── Yes → create JWT

What does bcrypt.compare() do?
During login, the user provides the plain password.
The server already has the stored password hash.
bcrypt compares them securely.
The result is essentially: true or: false
The server does not need to decrypt the stored password hash.

What is JWT?
JWT stands for:
JSON Web Token
A JWT is a token commonly used to represent authenticated identity and claims.
After successful login:
Credentials
↓
Verification
↓
JWT
The server gives the JWT to the client.

What is the purpose of a JWT?
The JWT allows the client to prove its authenticated identity on later requests.
The flow is:
Login
↓
JWT
↓
Client
↓
Future request
↓
JWT sent to server
↓
Server verifies JWT
↓
User identified

What is inside a JWT?
A JWT generally has three parts:
Header.Payload.Signature
The payload may contain claims such as:
user ID
role
issued time
expiration
Passwords and other sensitive secrets should not be placed in the JWT payload.
A JWT payload is encoded, not automatically encrypted.

What is an Access Token?
An access token is a token the client presents when accessing protected resources.
A common HTTP format is:
Authorization: Bearer <token>
The server extracts the token and verifies it.

How is a JWT created?
After a user's credentials are successfully verified:
User
↓
user.\_id
↓
JWT payload
↓
JWT signing secret
↓
JWT
The JWT should contain a stable identifier, usually the user's \_id.
For example, the payload may conceptually contain:
userId: User.\_id

Why use an Environment Variable for the JWT Secret?
The secret used to sign JWTs should not be hard-coded in source code.
Instead it should be stored in an environment variable such as:
JWT_SECRET
This keeps secrets out of the source repository.
The .env file should also be excluded from Git.

What is JWT Verification?
Creating the token is only half of authentication.
The server must verify the token on protected requests.
The flow is:
JWT
↓
jwt.verify()
↓
Valid?
├── No → 401
└── Yes
↓
decoded payload

What is Authentication Middleware?
Authentication middleware checks whether the incoming request contains a valid authentication token.
Its job is:
Read Authorization header
↓
Extract Bearer token
↓
Verify JWT
↓
Find user
↓
Attach user to request
↓
next()

What is req.user?
After the JWT is verified, the middleware can retrieve the corresponding user and attach it to the request.
Conceptually:
req.user now represents the authenticated user.
This allows later controllers and services to know who is making the request.

Why is req.user important?
Suppose a logged-in user creates a mission.
The client sends:
title
difficulty
The client should not decide:
createdBy
Instead:
JWT
↓
authMiddleware
↓
req.user
↓
req.user.\_id
↓
Mission.createdBy
This prevents the client from pretending to be another user.

Why should createdBy eventually come from the authenticated user?
Before authentication, the client could send:
createdBy: another user's ID
After authentication:
createdBy = req.user.\_id
The server determines the creator from the authenticated identity.
This is much safer.

Authentication Status Codes
400 Bad Request
The request data is malformed or missing.
Examples:
email missing
password missing
invalid registration data

401 Unauthorized
Authentication failed or is missing.
Examples:
invalid password
invalid JWT
expired JWT
missing authentication token

403 Forbidden
The user is authenticated but does not have permission to perform an action.
Example:
Normal user
↓
tries admin-only operation
↓
403

Remember:
401 → Who are you?
403 → I know who you are, but you're not allowed.

Important Security Rules
Passwords should never be returned in normal User API responses.
JWT secrets should never be committed to Git.
JWT payloads should not contain passwords or other sensitive secrets.
The server should not trust createdBy sent by an unauthenticated client.
Authentication and authorization should be handled on the server.

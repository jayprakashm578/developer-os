📖 Notes
1. The Problem With Long-Lived Access Tokens
A JWT access token that remains valid for a very long time creates a larger security window.
For example:
Long-lived access token
        ↓
Token gets stolen
        ↓
Attacker may use it
        ↓
Access remains possible for a long time
Therefore, access tokens are usually made relatively short-lived.

2. What Is an Access Token?
An access token is a credential used by the client to access protected API resources.
Example:
GET /api/missions/my
with: Authorization: Bearer <access-token>
The server verifies the token before allowing access.

3. What Is a Refresh Token?
A refresh token is a credential used to obtain a new access token.
It is not normally used to access ordinary protected API endpoints.
The basic idea is:
Access Token
→ access protected resources
Refresh Token
→ obtain new access token

4. Why Use Two Tokens?
Using two tokens solves an important problem.
We want the access token to be short-lived for security, but we also don't want users to log in with their password every time the access token expires.
Therefore:
Login
 ↓
Access Token + Refresh Token
Later:
Access Token expires
 ↓
Refresh Token
 ↓
New Access Token

5. Access Token vs Refresh Token
Access Token	Refresh Token
Used for API access	Used to obtain a new access token
Usually short-lived	Usually longer-lived
Sent frequently	Used less frequently
Protects API requests	Maintains login/session continuity
Should contain minimal claims	Needs stronger protection

The key distinction is:
Access token = access
Refresh token = refresh

6. Why Should Access Tokens Be Short-Lived?
Suppose an access token is valid for 15 minutes.
If it is stolen:
Stolen token
 ↓
short validity window
The potential attack period is smaller.
Compare this to:
Stolen token
 ↓
valid for 30 days
The second situation creates a much larger risk window.
Short-lived access tokens therefore help reduce the impact of token theft.

7. What Happens When an Access Token Expires?
Suppose:
Access token
Issued → 10:00
Expires → 10:15
At 10:16:
Protected request
       ↓
jwt.verify()
       ↓
Token expired
       ↓
401 Unauthorized
The client can then use its refresh credential to obtain a new access token.

8. Refresh Endpoint
A refresh endpoint can be created such as:
POST /api/user/refresh
Its responsibility is:
Refresh token
      ↓
Verify refresh token
      ↓
Identify user
      ↓
Generate new access token
      ↓
Return new access token


9. Complete Refresh Flow
The complete process is:
Login
 ↓
Access Token + Refresh Token
 ↓
Access Token used for API requests
 ↓
Access Token expires
 ↓
Client calls /refresh
 ↓
Refresh token verified
 ↓
User identified
 ↓
New access token generated
 ↓
Client uses new access token

10. Refresh Token Is Not the Same as Access Token
normal authentication middleware:
validateUser
is primarily designed to validate the access token used for protected resources.
The refresh endpoint has a different responsibility:
refresh credential
 ↓
validate refresh credential
 ↓
issue new access token

11. Token Expiration
JWTs can contain an expiration claim.
This allows the server to determine whether the token is still valid.
Conceptually:
Issued
   ↓
Expires
   ↓
Invalid
Once the token expires, verification should fail.

12. Why Expiration Is Important
Without expiration:
JWT
 ↓
valid indefinitely
That increases the consequences of token theft.
With expiration:
JWT
 ↓
valid for limited time
 ↓
expires
This limits the lifetime of the credential.

13. Refresh Token Lifetime
A refresh token normally lives longer than an access token.
For example:
Access Token
→ minutes
Refresh Token
→ days or weeks
These are illustrative values, not universal requirements.
The important principle is:
Access token → shorter lifetime
Refresh token → longer lifetime

14. Why Refresh Tokens Are More Sensitive
A refresh token can potentially be used to obtain new access tokens.
Therefore:
Refresh token stolen
        ↓
Attacker may obtain new access tokens
Because of this, refresh tokens need careful protection.

15. Secure Token Storage
For browser-based applications, refresh credentials are commonly stored in secure cookies.
Important cookie security attributes include:
HttpOnly
Secure
SameSite
These controls help reduce different categories of token theft and cross-site attacks when configured correctly.

16. What Is HttpOnly?
An HttpOnly cookie cannot normally be read directly by client-side JavaScript.
Conceptually:
Browser JavaScript
       ↓
      ❌
       ↓
HttpOnly cookie
The browser can still send the cookie with requests according to cookie rules.
This can reduce exposure from certain JavaScript-based token-stealing attacks.

17. What Is Secure?
A Secure cookie is intended to be sent only over HTTPS.
Conceptually:
HTTPS ✅
HTTP  ❌
This is especially important in production.

18. What Is SameSite?
SameSite controls aspects of when a browser sends cookies in cross-site requests.
It is an important security mechanism for reducing certain cross-site request attacks.
The important terms to remember are:
HttpOnly
→ protects against normal JavaScript access
Secure
→ HTTPS only
SameSite
→ controls cross-site cookie behavior

19. Logout With Stateless JWTs
With a purely stateless access JWT:
JWT issued
 ↓
server doesn't store it
 ↓
JWT remains valid until expiration
So logout can be difficult because the server doesn't automatically have a record of that individual access token that it can delete.
Once issued, it generally remains valid until it expires unless additional server-side controls are introduced.

20. Why Refresh Sessions Help With Logout
With a refresh-token/session system:
Logout
 ↓
invalidate refresh session
 ↓
new access tokens can no longer be generated
The existing short-lived access token can then expire naturally.
This gives the server more control over the login session.

21. Token Rotation
Refresh token rotation means replacing the refresh token when it is used.
Conceptually:
Refresh Token A
      ↓
used
      ↓
Refresh Token B
      ↓
Token A invalidated
The old token should no longer be accepted.
This can help reduce replay risks and allows the system to detect suspicious reuse in stronger implementations.

22. Why Store Refresh Sessions Server-Side?
A server-side session/refresh record can help with:
logout
revocation
device/session management
token rotation
detecting suspicious reuse
limiting active sessions
For example:
User
 ├── Laptop session
 ├── Phone session
 └── Tablet session
You can later revoke one specific session.

23. Multiple Devices
A user might log in from:
Laptop
Phone
Tablet
A mature authentication system can treat these as separate sessions.
For example:
Laptop → active
Phone → active
Tablet → revoked
This is much easier to manage when refresh sessions are represented server-side.

24. JWT Payload
access JWT may contain information such as:
userId
role
iat
exp
Keep the payload minimal.
Never put:
password
password hash
JWT secret
other highly sensitive secrets
into the token.

Remember:
JWT payload data is encoded, not automatically encrypted.
Therefore you should not treat the payload as secret storage.

25. Role Claims and Stale Tokens
Your application now has RBAC.
Suppose:
10:00
User role = admin
10:01
JWT generated with role = admin
10:05
Admin role removed
An old access JWT may still contain:
role = admin
until it expires.
This demonstrates why long-lived access tokens can create stale authorization information.

26. Why Short-Lived Access Tokens Help With RBAC
Suppose an access token lasts:
30 days
A role change could leave an old token carrying outdated claims for a long time.
If the access token lasts:
15 minutes
the stale claim has a much shorter lifetime.
This is one benefit of short-lived access tokens.

27. Refresh Endpoint Must Not Trust User ID
A dangerous design would be:
POST /refresh
userId = another user's ID
and then the server generates a token.
That would allow impersonation.
The server must instead determine the identity from a verified refresh credential.
The correct idea is:
Refresh credential
 ↓
verify
 ↓
identify user
 ↓
new access token

not:
Client sends user ID
 ↓
trust client
 ↓
create token
